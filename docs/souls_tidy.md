# OAS 御魂整理系统设计与技术指南

本指南详细剖析了 OnmyojiAutoScript (OAS) 项目中，针对式神录御魂整理功能（`SoulsTidy` 任务）的自动化流与底层逻辑设计。文档旨在帮助开发者和用户理解其图像识别策略、排序逻辑以及容错处理。

---

## 1. 系统导航与任务入口

御魂整理任务（`tasks/SoulsTidy/script_task.py`）的核心功能是自动打理冗余御魂。执行流程从式神录界面开始，按照以下步骤建立定位：

```
式神录界面 (page_shikigami_records) 
  └── 寻找并点击进入御魂主界面 (goto_souls)
        └── 判定贪吃鬼喂食开关 (enable_greed)
        └── 判定奉纳开关 (enable_maneki)
```

**界面稳定度校验**：
进入御魂主界面后，脚本会不断截屏校验 `I_ST_GREED`（贪吃鬼图标）与 `I_ST_TIDY`（整理按钮）的并存状态以确认定位成功。同时支持点击 `O_ST_OVERFLOW` 识别区域，用以跳过并自动关闭可能出现的“御魂已满或溢出”的系统遮挡弹窗。

## 2. 核心功能流实现

### 2.1 贪吃鬼自动喂食 (`greed_maneki` - 贪吃鬼阶段)
如果用户在配置中启用了 `enable_greed`：
1. **界面进入**：顺序点击 `I_ST_GREED` 进入贪吃鬼，然后点击习惯设置 `I_ST_GREED_HABIT`，确保处于最新的自动喂食配置中。
2. **喂食操作与计数限制**：
   - 脚本通过点击立即喂食 `I_ST_FEED_NOW` 触发逻辑，并将最大循环动作次数上限硬编码限制为 **3次**（`feed_count >= 3`），防止意外陷入死循环。
   - 在喂食动作之间，会动态捕捉和处理可能弹出的“未选定御魂/御魂已耗尽”警告 (`I_ST_UNSELECTED`)，以及常规系统确认框 (`I_UI_CONFIRM`)。

### 2.2 自动奉纳 / 招财猫 (`greed_maneki` - 奉纳阶段)
如果用户在配置中启用了 `enable_maneki`：
1. **模块跳转**：自动点击关闭贪吃鬼面板并切入奉纳界面，直到成功检测到 `I_ST_CAT`（招财猫）为止。
2. **状态锁定（弃置界面）**：
   - 奉纳只奉纳已被弃置的御魂。脚本会循环尝试点击 `I_ST_ABANDONED_SELECTED`（已弃置选择卡），直到状态切换完毕。
3. **关键步骤：OCR 等级排序验证**：
   - 奉纳御魂必须优先奉纳低星/低等级（特别是 +0 御魂），以防误伤高强御魂。
   - 脚本会跑一个循环校验当前的排序标签是否为“按等级”。如果未识别到等级排序 `O_ST_SORT_LEVEL_1`，它会轮流点击不同的排序按钮（时间排序 `O_ST_SORT_TIME`、类型排序 `O_ST_SORT_TYPE`、位置排序 `O_ST_SORT_LOCATION` 等），直到成功切换并识别出等级排序为当前激活状态。
   
#### 4. 奉纳策略与防误伤双保险：
在开始奉纳时，OAS 支持两种识别与选定策略：
* **策略 A：御魂堆叠奉纳 (Soul Stack)**：检测到 `I_ST_SOUL_STACK` 时，使用系统堆叠大批量奉纳。
* **策略 B：常规单个 +0 选定与 OCR 双校验**：
  - 首先使用模板匹配定位首个御魂的强化等级为 +0 (`I_ST_LEVEL_0`)。如果发现首个御魂不是等级 0，将立即打印日志退出（"First Orichi isn't Level 0, quit"），避免高强御魂损失。
  - **OCR 中文字符纠偏（趣味细节）**：
    由于阴阳师游戏中御魂左下角强化的“+0”字体渲染较为艺术化，OCR 识别引擎在特定分辨率下极易将“+0”误识为汉字“古”字。
    在代码中，OAS 特意做了一层纠偏验证：
    ```python
    firvel = self.O_ST_FIRSET_LEVEL.ocr(self.device.image)
    if firvel != '古': 
        # 当 OCR 识别出的等级不再是代表 "+0" 的 "古" 字时，认为已无零级御魂，退出奉纳
        logger.info('No zero level, bongna done')
        break
    ```

### 2.3 奉纳执行与罕见“神赐”礼包领取
当满足奉纳条件后：
1. 脚本会执行长按 `L_ONE` 动作进行批量选中。
2. **金币比对**：通过 OCR 区域 `O_ST_GOLD` 检测金币预期值，确保存在待奉纳产出后，点击奉纳按钮 `I_ST_DONATE`。
3. **神赐奖励处理**：
   - 大批量奉纳时可能会触发游戏内罕见的“神赐”大奖特效（弹出一个全屏神赐奖励卡牌，会挡住所有操作）。
   - 脚本对此设计了强效容错：通过 `I_ST_GOD_PRESENT` 判定神赐界面出现，并自动定位点击 `C_ST_GOD_PRSENT` 将其收下并点按空白处消除卡牌，从而恢复整理循环。

## 3. 开发者提示与改进空间

> [!WARNING]
> * **金币检查缺失**：在目前版本的 `script_task.py` 奉纳逻辑中，缺少关于金币数量上限或下限的二次验证（仅能验证 gold 识别值非零）。当用户身上金币已溢出或有其他异常弹窗时，可能会产生盲目点击。
> * **“古”字硬编码强绑定**：该 OCR 校验属于高耦合方案，若未来游戏升级更改御魂等级字体或 OCR 字体库更新，可能导致奉纳逻辑在首个御魂处提前中断。重构时推荐使用更稳健的区域特征模板匹配或纯数字 OCR 过滤器。
